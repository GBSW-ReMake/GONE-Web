# GONE Web 프론트엔드 문서

GONE Web의 기능 계획, 구현 중 발견한 이슈, 최종 개발 결과를 기록한다.

## 문서 구조

```text
docs/fe/
├── README.md
├── plans/
│   ├── _TEMPLATE-plan.md
│   └── feat-{이슈번호}-{기능명}.md
├── issues/
│   ├── _TEMPLATE-report.md
│   └── issue-{이슈번호}-{기능명}-{설명}.md
└── reports/
    ├── _TEMPLATE-final-report.md
    └── feat-{이슈번호}-{기능명}-final-report.md
```

## 작성 순서

1. 계획서를 작성한다.
2. 기획·디자인·백엔드 의존성을 확인한다.
3. 담당자 검토를 받는다.
4. GitHub Issue와 브랜치를 만든다.
5. 구현과 QA를 진행한다.
6. 발견한 문제를 이슈 보고서에 기록한다.
7. 최종 보고서를 작성한 뒤 PR을 올린다.

## 파일명 규칙

- 기능 계획서: `feat-{이슈번호}-{기능명}.md`
- 버그 보고서: `issue-{이슈번호}-{기능명}-{설명}.md`
- 최종 보고서: `feat-{이슈번호}-{기능명}-final-report.md`
- 기능명은 짧고 명확한 한글 케밥 표기법을 사용한다.

## 기록 원칙

- 계획과 구현이 달라지면 계획서의 변경 내용을 갱신한다.
- 확정되지 않은 API·정책은 추측하지 않고 `결정 필요`로 표시한다.
- 화면 상태는 정상·로딩·빈 상태·오류·권한 거부를 모두 기록한다.
- 문서에는 관련 Issue, PR, Figma, Notion 링크를 남긴다.
