# GONE Web 개발 워크플로우

기능 하나는 계획서부터 개발자 병합까지 아래 11단계를 순서대로 진행한다.

```text
계획서 작성 → 계획서 검토 → GitHub Issue → 브랜치 분기 → 기능 개발
→ QA 및 이슈 보고 → 수정 → 최종 보고 및 검토 → 최종 커밋·Push
→ PR → 개발자 병합
```

## 1. 계획서 작성

- 위치: `docs/fe/plans/`
- 목적, 사용자 시나리오, 화면·상태, API·권한, 작업 목록, 완료 기준을 작성한다.
- API가 미확정이면 추측하지 않고 의존성과 결정 필요 항목으로 기록한다.
- 파일명은 `feat-{이슈번호}-{기능명}.md`로 작성한다.

## 2. 계획서 검토

- Notion 요구사항, Figma 화면, GONE Server API를 함께 확인한다.
- 담당자에게 계획서 검토와 승인을 받는다.
- 승인 전에는 Issue, 브랜치, 구현을 시작하지 않는다.
- 구현 범위나 정책이 바뀌면 계획서를 먼저 갱신한다.

## 3. GitHub Issue 작성

- 기능: `기능 추가` 템플릿
- 버그: `버그 리포트` 템플릿
- 설정·문서·리팩터링: `작업·문서` 템플릿
- 제목: `[feat] 기능명`, `[fix] 버그 설명`, `[chore] 작업명`
- 본문: 배경, 사용자 흐름, 작업 범위, 완료 조건, 관련 링크를 포함한다.
- 계획서와 Issue가 서로 다른 내용을 갖지 않게 한다.

## 4. 브랜치 분기

```bash
git checkout dev
git pull origin dev
git checkout -b feat/<이슈번호>-<기능명>
```

- 기능: `feat/{이슈번호}-{기능명}`
- 버그: `fix/{이슈번호}-{설명}`
- 문서·설정: `docs/{이슈번호}-{설명}` 또는 `chore/{이슈번호}-{설명}`

## 5. 기능 개발

- `pages`, `components`, `api`, `stores`, `types`의 책임을 지킨다.
- 화면에서 직접 Axios를 호출하지 않고 `src/api`의 함수를 사용한다.
- 정상·로딩·빈·오류·권한 상태를 처음부터 구현한다.
- 커밋 하나에는 하나의 논리적 변경만 포함한다.
- 미사용 변수·함수는 ESLint 경고를 확인하고 필요 없는 코드는 제거한다.

## 6. QA 및 이슈 보고

- 정상·로딩·빈·오류·권한 거부·인증 만료 상태를 확인한다.
- 반응형, 키보드 접근성, 주요 브라우저 동작을 확인한다.
- 발견 이슈는 `docs/fe/issues/` 템플릿으로 기록한다.
- Critical·Major 이슈는 담당자와 수정 방향을 먼저 확정한다.

## 7. 수정

- Minor 이슈: 현재 기능 브랜치에서 수정한다.
- Major 이슈: 담당자 결정에 따라 현재 브랜치 또는 별도 `fix/*` 브랜치를 사용한다.
- 수정 후 동일한 재현 절차로 재검증한다.
- QA 보고서에 원인, 수정 파일, 재검증 결과를 남긴다.

## 8. 최종 개발 보고 및 검토

- 위치: `docs/fe/reports/`
- 구현 내용, 계획 대비 변경점, API·권한, QA 결과, 제한사항을 기록한다.
- 관련 Issue·PR·Figma·Notion 링크를 연결한다.
- 담당자에게 최종 보고서 검토를 받는다.

## 9. 최종 커밋 및 Push

```bash
pnpm lint
pnpm format:check
pnpm build
git status
git add <변경 파일>
git commit -m "feat: 기능 구현 완료 (#12)"
git push origin feat/12-기능명
```

- 검증 결과가 통과한 뒤 Push한다.
- `git diff --staged`로 의도하지 않은 파일을 확인한다.
- 작업 성격이 섞이지 않도록 의미 있는 단위로 커밋을 나눈다.

## 10. PR 생성

- Base: `dev`
- Compare: 작업 브랜치
- 제목: `type: 작업 내용 (#이슈번호)`
- 본문: [PULL_REQUEST_TEMPLATE.md](PULL_REQUEST_TEMPLATE.md)를 사용한다.
- 변경 내용, 테스트 방법, QA 상태, API·문서 검토 결과를 작성한다.
- `Closes #이슈번호`로 Issue를 연결한다.

## 11. 개발자 병합

- 담당 개발자가 코드 리뷰, CI, QA 결과, 문서를 확인한다.
- 수정 요청이 있으면 반영 후 다시 검토를 받는다.
- 승인 후 `dev`에 병합한다.
- 병합 뒤 작업 브랜치는 삭제한다.
- 에이전트는 사용자가 명시적으로 요청하지 않는 한 병합하지 않는다.
