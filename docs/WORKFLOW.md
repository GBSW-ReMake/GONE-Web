# 프론트엔드 개발 워크플로우

기능 하나는 계획부터 `dev` 병합까지 아래 순서로 진행한다.

```text
계획서 작성
→ 기획·디자인·API 검토
→ GitHub Issue 생성
→ 브랜치 생성
→ 구현
→ QA 및 이슈 보고
→ 수정·재검증
→ 최종 보고서
→ 커밋·Push
→ dev 대상 PR
→ 리뷰·CI·개발자 병합
```

## 시작 전

- Notion에서 사용자 흐름과 정책을 확인한다.
- Figma에서 화면과 상태를 확인한다.
- GONE Server에서 Endpoint·권한·응답을 확인한다.
- 계획서의 결정 필요 항목을 담당자에게 확인한다.

## 계획서와 구현

- 계획서는 `docs/fe/plans/`에 작성한다.
- 계획서에 작업 범위, 화면 상태, API, 권한, 완료 기준을 적는다.
- 계획과 구현이 달라지면 문서를 먼저 갱신하고 변경 이유를 남긴다.
- 작업 중 발견한 문제는 `docs/fe/issues/`에 기록한다.

## 커밋과 PR

- 한 커밋에는 하나의 논리적 변경만 담는다.
- 커밋 제목에 관련 Issue 번호를 포함한다.
- PR Base는 `dev`, Compare는 작업 브랜치로 설정한다.
- PR에는 변경 내용, 검증 방법, 화면 변화, 관련 문서와 `Closes #이슈번호`를 작성한다.
- 개발자 리뷰와 CI 통과 후 담당자가 병합한다.
